# commit-kind

A small Python CLI and library that classifies git commit messages by type (`feat`, `fix`, `docs`,
`refactor`, `test`, `chore`) with a transparent, rule-based classifier. Every prediction names its rule.

## Install

Python >= 3.10, no runtime dependencies. In a venv: `python3 -m pip install .`. Or run without installing:

```
PYTHONPATH=src python3 -m commit_kind --version
```

## Usage

```
$ commit-kind classify "fix: handle empty input"
fix
$ commit-kind classify --json "fix: handle empty input"
{"evidence": "fix:", "label": "fix", "rule": "prefix.fix"}
$ commit-kind classify --explain "add retry to the client"
feat because the verb phrase "add" matched (rule ambiguous.add)
$ printf 'docs: reword the intro\n\nBody.\n' | commit-kind classify -
docs
$ commit-kind classify ""
classify: error: empty commit message
```

`-` reads all of stdin as one message. Exit codes: 0 ok, 1 empty message, 2 usage error (errors go to
stderr, stdout stays empty). `--json` and `--explain` exclude each other.

## How it decides

1. The Conventional Commit prefix, if there is one (scope and `!` allowed). `perf` maps to `refactor`;
   `style`, `build`, `ci` and `revert` map to `chore`.
2. Otherwise the leading verb ("handle", "extract", "bump", ...).
3. Ambiguous verbs such as "add" are resolved by their object ("add tests" is `test`, "add retry" is `feat`).
4. Otherwise an object word in the summary; if nothing matches, `chore`.

Only the first non-blank line (the summary) is read. The rules live in `src/commit_kind/rules.py`.

## Check and eval

```
./scripts/check.sh
```

Runs ruff, ruff format, mypy (strict), pytest and the eval; exit 0 only if all pass. Set `PYTHON=` to
choose the interpreter. `PYTHONPATH=src python3 -m commit_kind eval` prints:

```
strategy                    accuracy              macro_f1            min_recall   misleading_accuracy
threshold                     0.8500                0.8500                0.7000                0.7000
majority                 0.1667 fail           0.0476 fail           0.0000 fail           0.1667 fail
keyword_spam             0.5389 fail           0.5454 fail           0.4000 fail           0.0000 fail
random                   0.1667 fail           0.1671 fail           0.1333 fail           0.1333 fail
rules                    1.0000 pass           1.0000 pass           1.0000 pass           1.0000 pass
controls must fail every metric; the classifier must pass every one
eval passed
```

It scores the test split on accuracy, macro-F1, min recall and misleading-slice accuracy. The three negative
controls (majority class, keyword spam, random) must fail every metric; the classifier must pass all of them
and not fall below `evals/baseline.json`. Exit codes: 0 pass, 1 gate failed, 2 usage, 3 bad or missing
config, dataset or baseline. The thresholds in `evals/config.json` were approved by the owner on 2026-10-25.
Tune on dev with `--split dev --show-errors`; `--write-baseline --block B<n>` rewrites the baseline.

## Limits

- The data (`data/commits.jsonl`, 360 messages, fixed seed) is synthetic, generated by this project's own
  templates (`scripts/generate_dataset.py`). No real repository data is used.
- The rules were tuned on dev only, but dev and test come from the same generator and share templates. The
  1.0 eval score therefore says little about real repositories.
- The B2 review found that a first-word lookup fitted on dev would also have passed all four thresholds on
  the first version of the dataset (`.planning/B2/REVIEW.md`). No number is quoted, because the data was
  regenerated afterwards.
